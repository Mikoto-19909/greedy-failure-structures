# 用保度反例检查 R3 的机制解释

`r3-pair` 为 R3 提供小实例选例和机制解释检查：固定每个集合大小、每个元素频数、全集、
集合数、预算 k 和标签，寻找 E0 与首步不可恢复性之间的成对见证。
它不修改 R2/R3 正式入口或设计，不生成正式确认样本，也不估计协议效果。

## 先跑两个例子

从反例工具工作树根目录，在 PowerShell 中运行：

```powershell
.\counterexamples.ps1 r3-pair --same-optimum
.\counterexamples.ps1 r3-pair --input designs/r3_lower_e0_example.json --target lower-e0-worse --same-optimum
```

输出目录自动命名，每次单独保存。终端会打印可直接执行的 `show` 命令；
`show` 会独立重算整个已搜索前缀和交换路径，再展示两侧集合、Greedy 轨迹和最优见证。
其他平台使用 `python counterexamples.py`。

第一个默认例子搜索 **E0 相同但首步结局不同** 的配对：

```text
原始：S0={0,1}, S1={0,2}, S2={1,3}, k=2
配对：S0={0,1}, S1={2,3}, S2={0,1}, k=2

两边逐集合大小都是 [2,2,2]，逐元素频数都是 [2,2,1,1]。
两边 E0=2、O=4。
原始 O1=3，首步不可恢复；配对 O1=4，首步可恢复。
```

只需在集合 1、2 之间交换元素 0、3。这个例子同时改变了重复集合数：
原来三个集合不同，配对后只有两个不同集合；输出会明确记录这一变化。
保度并不等于只改变一个结构性质。

第二个例子是开发时选出的功能夹具，不是随机抽样数据。它在 **O=8 不变** 的情况下找到：
原始 `E0=5,O1=8`，配对 `E0=4,O1=7`。因此较低 E0 的端点反而首步不可恢复。
这说明低 E0 不能逐实例保证安全，不否定某种随机协议可能具有平均优势。

## 对齐 R3 的指标

R3 的主事件是首步不可恢复，不能直接用最终 Greedy 失败代替。
本工具要求输入集合等长；项目标准 Greedy 平局选最小索引，所以首步选集合 0。

- `G`：标准 Greedy 最终覆盖值。
- `O`：不加额外限制的精确最优覆盖值。
- `O1`：强制包含集合 0，仍选择恰好 k 个不同集合时的精确最优覆盖值。
- `E0 = Σ_{a∈S0}(r_a−1) = Σ_{j>0}|S0∩Sj|`，其中 `r_a` 是元素 a 属于的集合数。

同一元素在其他集合中出现 `r_a−1` 次，所以两种 E0 计算方式相等。
`O1<O` 表示首步不可恢复；`G<O` 表示最终失败。因为 Greedy 保留了集合 0，
必有 `G≤O1≤O`：首步不可恢复蕴含最终失败，反向不成立。
输出也单列“首步可恢复但最终失败”，避免混用两个指标。

目前有三种目标，都比较原图与一个可达变体：

- `same-e0-flip`（默认）：E0 相同，`O1<O` 的真假不同。检查 E0 是否足以判别首步结局。
- `lower-e0-worse`：较低 E0 的端点首步不可恢复，较高 E0 的端点可恢复。
  检查“越低 E0 就一定越安全”这种逐实例解释的反例。
- `first-step-flip`：只要求首步结局不同，不限制 E0 的关系。

`--same-optimum` 额外要求两边 O 相同。默认不要求，因为 R3 对每个端点分别求自己的 O。
这些目标不是正式确认的主估计量，也不通过寻找反例来决定正式效应方向。

## 用自己的 R2/R3 相关实例

```powershell
.\counterexamples.ps1 r3-pair --input 'my-data/instance.json' --target first-step-flip
.\counterexamples.ps1 r3-pair --input 'my-data/paths.jsonl' --record 17 --target same-e0-flip
.\counterexamples.ps1 r3-pair --input 'my-data/r2-graph.json' --k 4 --target lower-e0-worse
```

支持项目标准实例 JSON（也可以有外层 `instance` 对象）、R1/R1c 的逐行实例，
以及 R2 保存的 `task.n + sets` 原图对象。`--record` 指 JSONL 的实际物理行号，
空行或不存在的行号会拒绝。多预算 R2 原图必须显式指定 `--k`，不会暗取诊断预算。
`--k` 也可以覆盖单实例原本的预算，实际选择会保存到结果中。

导入只读取实际集合和必要维度，并保留源路径、行号及任务标签；旧的 G/O、状态和种子标签
不构成本工具的正确性依据，也不会据此声称验证了整个 R2 实验。所有覆盖值和见证重新计算。
非等长输入会拒绝，以免把“固定包含集合 0”误称为 Greedy 的实际首步。
第一版支持最多 64 个元素、32 个集合，精确组合预算另行限制。

R2 探索原图可以用于追加解释，但不能重新标成独立 R3 探测或确认样本。
默认演示只使用随工具提供的功能夹具，不访问正式确认种子或生成流。

## 搜索方法和预算

每个合法交换选择两行 i<j，并选 `a∈Si\Sj`、`b∈Sj\Si`，将 a 从 Si 移到 Sj、
同时将 b 从 Sj 移到 Si。两行各失去和得到一个元素，两列各失去和得到一条连接，
因此逐项两侧度数保持不变。集合索引和元素标签不重排，允许重复集合。

工具按 `(i,j,a,b)` 字典序枚举合法交换，以广度优先顺序检查不同状态，不做同构去重。
每个新状态完成精确评估后与原图比较，找到第一个满足目标的配对就停止。
保存的路径是这次搜索实际发现的路径。

```powershell
.\counterexamples.ps1 r3-pair --max-states 500 --max-switches 20000 --same-optimum
```

- `--max-states` 默认 200，包含原图；达到上限后遇到下一未访问状态即停止。
- `--max-switches` 默认 10,000，计数所有已检查的合法交换，包括到达重复状态的交换。
- `--max-combinations` 默认 200,000，限制每次精确最优枚举的组合数。
  O1 还需受限枚举，成本计入实际运行；超限在搜索前拒绝，不把未完成解当作精确值。

状态 `pair_found` 表示已找到并验证配对；`state_budget_exhausted` 和
`switch_budget_exhausted` 表示尚未完成。`component_exhausted` 只表示穷尽了从这个原图
通过所定义合法交换可达的状态，没有找到所选目标，不推广到其他原图。
没有合法交换时，原图一个状态就可以得到这个结论；预算耗尽不能用来声称无交换空间。
所有列度相同时 E0 必然固定；工具保留这类输入及其实际搜索结果。

计数不是墙钟时间上限，独立验证还需重算一次已搜索前缀；加预算会从头搜索，不是续跑。
此 BFS 枚举合法交换，和 F3 的随机行列提议、非法提议计入链长、按 E0 方向接受的协议不同。
按结局选择端点所得的样本不能拿去估计 F3 的协议均值或置信区间。

## 输出如何帮助 R3

- `pair.json`：原图、配对、搜索设置、来源、停止状态、计数、交换路径和全部核验指标。
- `original.json` / `counterexample.json`：可用现有 replay 命令重放的两侧实例；未找到时无后者。
- `README.md`：E0、G、O、O1、首步与最终失败，以及行列度、全局交集总量、交集分布、不同集合数。

全局交集总量 `Σ_a C(r_a,2)` 在保度时固定；局部 E0、交集分布和重复情况仍可能变化。
可用这些差异检查某种解释是否遗漏了其他结构变化。工具并不声称穷尽所有结构性质。

独立验证器使用普通集合与 2×2 成员关系检查重新生成搜索前缀，核对首个配对、状态、计数，
逐项核对行列度和全局交集总量，并用组合枚举重算 O/O1、规范见证和 Greedy 决策。
它复用已有独立集合验证器的格式解析与计算，不调用本工具的生产搜索、交换或匹配函数。
手动复核命令为：

```powershell
python analysis/validate_r3_counterexamples.py --input '结果目录/pair.json'
```

先用这些见证修正逐实例机制解释，或作为正式实现的已知答案与拒绝测试材料；
是否进入正式确认、采用哪种协议和如何推断，仍由 R3 的专项设计决定。
普通反例缩小器会改变两侧度数，不应直接用于保度见证后继续声称保持了 R3 的条件。
