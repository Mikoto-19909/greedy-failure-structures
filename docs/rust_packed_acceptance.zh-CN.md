# 紧凑结构计数：测试计划与验收

基线为 `7387f43d2133ebdbd8dfdf724c9f4e47af10eaad`，旧扩展为 0.2.0。
范围限于结构计数传输和中间对象生命周期；在原工作树、原分支实施。

## 两阶段候选

1. 保留旧 `native.counts`，新增 `counts_packed`：频数列表、little-endian `<QQ>` 配对 bytes、严格支配数。
   每条记录为交集/非零并集两个 u64，按原输入配对顺序写入，不额外保存完整 Rust 元组向量。
   Python 仍采用原除法、Jaccard 列表和 `math.fsum`，先验证传输改变。
2. 在第一步精确一致后，用一次性迭代器按同顺序交给 `math.fsum`，有效配对数从已验证的16字节记录数得到。
   空载荷仍返回平均值 None；长度错误、记录数超过可用配对数及计算异常必须明确失败。

新适配器要求扩展提供 `counts_packed`，旧 wheel 缺接口时给出重建提示；不回退到 Python 或旧计数路径。
默认 Python、Gini、Greedy/Lazy、注册表、配置、CSV 身份和续跑语义保持不变。

## 正确性与兼容性

- 旧 counts 和新 bytes 解码结果逐字段、逐记录比对，并用独立集合定义核对频数/交并/严格支配。
- 覆盖空/重复/嵌套集合、全零和单候选、各位宽边界、计数 255/256/257、65535/65536/65537 的字节序。
- 复用保存的28个输入和原答案；公开结果全字段精确相同，浮点不放宽容差。
- 检查非法输入、非法尾位、错误 payload 长度/记录数、缺接口、不可调用接口、错误传播和出错后恢复。
- 证明候选调用 counts_packed、基线调用旧 counts；流式求和不得先消耗迭代器再计数。
- 执行严格 Rust 专项、全回归/mypy、格式/clippy、干净 wheel 环境和跨平台 CI；独立代理执行有效及无效案例。

## 性能与内存门槛

主要比较使用冻结旧源码/旧 wheel 与候选 wheel 的独立持久进程。进程启动、数据读入、预热和正确性核对不计时；
每例10对、两种顺序各5对，记录每次公开 `analyze_instance` 的耗时和实际原生入口调用次数。
小实例用批次测量减少计时器噪声，两个进程串行应答，不并发测量。
仅将本次创建的测量进程固定到同一可用逻辑 CPU 并记录掩码；不改变其他进程或全局电源设置。

- 两个1000集合例分别要求配对加速比中位数 ≥1.20，两个独立轮次均满足，不能合并掩盖单例回退。
- 小/稀疏例若中位耗时增加 >10%，均标记并复测定位；单独报告绝对变化，不自动豁免微秒级案例。确认稳定回退后停止接入，保留失败记录。
- 两个大例分别要求 Python 分配峰值下降 ≥50%。tracemalloc 与自然 OS 进程峰值在不同子进程测，
  后者明确标注含启动/输入的生命周期峰值，不解释为函数独占内存。
- 先测紧凑+列表，再测紧凑+流式，区分收益来源。计时不与回归/编译并行。

任何正确性差异先修复；性能或内存未达门槛则报告未通过，不自动切换默认后端或扩大算法范围。
用维护入口复现，临时环境/构建/探针在完成后归档或回收，保留原始数据与必要源码快照。

## 执行结果（2026-09-21）

候选满足本轮预先设定的本地正确性、性能和内存门槛。生产扩展为0.3.0，默认 Python 保持不变。
紧凑+列表阶段先通过23项专项和28例精确对照；最终流式候选通过24项专项（含干净wheel环境）。
完整回归603项：598通过、5项原有可选跳过；mypy 42个源码文件通过，Rust格式与clippy通过。
独立代理复核4096个结构穷举、60个边界、808个非法原生调用、9个异常载荷及3320个同顺序比值；
真实旧wheel重现28答案，新适配器明确拒绝旧接口，默认无扩展路径正常。未检出计算差异。

### 实际公开入口计时

下表均为同轮旧0.2.0/新0.3.0独立进程的公开结构调用，固定同一逻辑CPU；配对倍率单独取中位数。
第一轮同时保留紧凑+列表的中间态，第二轮确认最终流式候选；不同阶段的绝对时间不能直接当作配对比较。

| 轮次 | 输入 | 旧中位数/ms | 候选中位数/ms | 配对加速中位数 | 更快对数 |
| --- | --- | ---: | ---: | ---: | ---: |
| round1 | 稠密(4097,1000,100) | 130.087 | 76.894 | 1.699 | 10/10 |
| round1 | 重复(4097,1000,100) | 125.732 | 72.270 | 1.728 | 10/10 |
| round1 | 稀疏(65537,160,40) | 27.591 | 27.191 | 1.038 | 8/10 |
| round2 | 稠密(4097,1000,100) | 138.392 | 79.578 | 1.746 | 10/10 |
| round2 | 重复(4097,1000,100) | 136.588 | 79.577 | 1.709 | 10/10 |
| round2 | 稀疏(65537,160,40) | 29.410 | 28.856 | 1.016 | 8/10 |

两个大例两轮均超过1.20倍且每例10/10对更快。全部28例未触发中位耗时增加>10%的标记，
但少数小例略慢，按中位耗时比第一/第二轮最差约+0.885%/+3.457%；不能说所有输入都更快。
稀疏收益很小，部分单对变慢。结果只覆盖本机、固定语料及此公开函数，不代表全实验流程加速。

MB=10^6字节，每格每轮一个独立进程。Python分配跟踪和无跟踪OS峰值分别执行。

| 轮次/输入 | Python峰值：旧/候选 MB | 下降 | 自然进程总峰值：旧/候选 MB |
| --- | ---: | ---: | ---: |
| round1/稠密 | 76.34 / 8.74 | 88.55% | 131.41 / 57.41 |
| round1/重复 | 76.33 / 8.73 | 88.56% | 131.13 / 57.28 |
| round2/稠密 | 76.34 / 8.74 | 88.55% | 130.75 / 57.37 |
| round2/重复 | 76.33 / 8.73 | 88.56% | 132.80 / 57.38 |

中间列表阶段的大例Python峰值约24.39MB，最终流式约8.74MB；这是独立内存观测，不能把跨阶段计时直接相减作额外加速比。
OS峰值包含启动、加载输入和模块，是进程生命周期峰值，不是函数独占量或保证上限。编码字节仍为O(m²)，未消除二次复杂度。

## 复核与复现

独立代理重新计算1680条计时、50条内存记录及全部汇总；每次测量由driver强制检查原生入口与答案，
版本/安装路径/CPU约束及候选源码快照一致。历史剖析工具已固定旧适配器，并通过故障注入确认替换仍有效，避免新旧实际走同一路径。

维护入口为 `experiments/rust_profile/accept_packed.py`，环境准备和可运行示例见其同目录 README。
本次输入和原答案复用 `results/rust_algorithms_large_isolated_20260919/`；原始两轮记录、源码、日志与独立复核在
`results/rust_packed_acceptance_20260921/`。可选 `--list-adapter` 使用第一轮 source 中保存的中间态源码。
测量启动、I/O、预热和核对均不计时，工作进程顺序应答，没有并发运行两侧内核。
数据仍为本机未发布证据；实际远端检查以本次提交的PR状态为准。临时环境与构建输出在确认后回收，保留wheel、输入、源快照与原始记录。
