# Rust 性能归因与下一步结论

本文记录 2026-09-20 的诊断阶段。2026-09-21 的生产候选与独立旧/新 wheel 验收见
[紧凑候选验收](rust_packed_acceptance.zh-CN.md)，下述历史计时不替代新候选的验证。

当前应优先优化结构计数的传输形式及对象生命周期。继续迁移更多算法尚缺乏本轮调用链以外的热点证据。
稀疏 Lazy 的问题主要是转换/解码及调用边界，并非选择循环；缓存原生输入是后续候选，但要连同构造和 Python 封装成本评估。
本轮只增加隔离诊断扩展与剖析入口，没有修改生产内核、默认后端、数学定义或浮点汇总顺序。

## 基线与方法

- 收口基线：`9d715f56f3076bf82fea59a39180055e01ce614a`，草稿 PR #69；独立复核及该提交的 Ubuntu/Windows 原生、核心、研究、类型检查均通过。
- 本机 Windows x64、Intel Core i9-13900HX、Python 3.12.14、Rust 1.95.0、release wheel。未固定 CPU 频率/亲和性，配对交替减小漂移，不外推其他硬件。
- 精确复用已有 24+4 个固定实例和参考答案，覆盖随机、高重叠、重复、包含、较大稠密和稀疏输入。
- 首轮 15 项操作各预热一次、测量 10 轮，正反顺序交替；便宜转换探针每轮调用 50 次，共 4,200 条记录。
- 紧凑对照保留生产 `analyze_instance`，仅在独立进程中临时替换其原生 counts 返回通道。整数交并计数及配对顺序不变，Python 仍计算除法、列表、math.fsum、Gini 和结果对象。
- 两轮紧凑对照各 560 条记录，最终采用 `packed-final`；每实例 10 对原/原型调用交替。核对与写盘均在计时之外。全部非计时输出与原答案精确一致。
- 独立代理复算所有中位数、配对倍率与内存分组；另对 30 个有效边界、5 个非法输入核验紧凑通道，并确认替换正常恢复。代理复核不等于外部同行评审。

## 稀疏 Lazy 的退化

在 `(65537,160,40)` 上，首轮公开 Python/Rust Lazy 分别为 0.518/2.024 ms。
仅 Python 编码为 0.677 ms；直接原生调用 0.853 ms；Prepared 稳态调用 0.142 ms。
诊断调用内，解码中位数 0.441 ms，队列初始化 0.086 ms，选择循环 0.027 ms。
因此单独优化选择循环难以消除这例退化。Prepared 排除了一次构造，尚未实现公开 API、跨进程生命周期或完整工作流收益，不能把稳态倍率当作实际产品加速。

## 大规模结构计算与紧凑传输

大稠密和重复两例中，按三个公开函数各自中位数的合计，结构调用占 95.7%/95.8%。复用解码几乎不改善 counts：原生/Prepared 约 0.999/1.013 倍。
诊断配对扫描本身仍占显著时间；参数与结果转换、局部释放等混合残差约占一半。该残差不是纯 boxing 耗时。
原接口为每对返回 Python 元组及整数对象，之后还保留 Jaccard 浮点列表。原型改为 little-endian u64 对的连续 bytes，再由 Python 按原顺序迭代。

| 输入 `(n,m,k)` | 原 Rust 结构/ms | 紧凑原型/ms | 配对倍率中位数 |
| --- | ---: | ---: | ---: |
| high_overlap (257,100,20) | 0.460 | 0.352 | 1.327 |
| timing_dense (1024,300,40) | 5.936 | 4.608 | 1.285 |
| timing_dense (4097,1000,100) | 115.602 | 74.858 | 1.543 |
| timing_sparse (65537,160,40) | 25.777 | 25.512 | 1.008 |
| timing_duplicates (4097,1000,100) | 107.264 | 74.266 | 1.457 |

两个 1,000 集合实例最终均为 10/10 对更快；首轮相同两例为 1.461/1.624 倍，最终为 1.543/1.457 倍，方向一致但绝对计时会漂移。
稀疏结构例最终仅 1.008 倍、范围 0.988–1.063，视为接近波动范围。最小实例的绝对时间很短，不能据此承诺普遍收益。
这是结构函数相对已有 Rust 路径的收益，不是整个项目、完整 runner 或 R2 的加速。原型仍先生成 Rust 配对向量，没有消除二次复杂度或 O(m²) 存储。

## 内存

每格在独立子进程测一次。Python 跟踪与无跟踪的 OS 测量分开执行；下表 MB=10^6 字节。

| 输入 | Python 分配峰值：原/原型 MB | 无跟踪进程总峰值：原/原型 MB |
| --- | ---: | ---: |
| timing_dense | 76.34 / 24.34 | 130.36 / 70.97 |
| timing_duplicates | 76.33 / 24.33 | 131.92 / 71.51 |

Python 峰值下降约 68.1%，但不包含 Rust 分配。OS 数值包含解释器启动和输入加载，调用前生命周期峰值约 52 MB，不能解释为函数独占内存。小实例未超过先前峰值不等于零分配。
首轮 baseline 中开启 tracemalloc 后读出的 OS 峰值包含跟踪器开销，未用于上述自然进程内存结论。

## 下一步与停止条件

1. 第一优先级是把紧凑配对通道做成小范围生产候选，保留原始 counts 接口、Python 浮点顺序和独立验证，另做宽度/长度错误拒绝及包装回归。
2. 第二优先级是研究同一实例多算法调用时复用编码/解码；必须计入创建、结果组装、内存与进程边界，不能只引用 Prepared 稳态时间。
3. 继续保持显式后端。当前证据不支持自动切换全部输入，也不支持把范围扩大到其他算法、精确求解器、随机数或调度/身份规则。
本轮已经得到可复核的瓶颈解释和优先级，因此停止继续扩大试验；两个候选均未接入生产路径。

## 复现与保存

在隔离 Python 环境中安装生产及诊断扩展；需要 Rust 与平台链接器、完整 Git 历史。

```console
python -m pip install ./native/structure ./experiments/rust_profile
python scripts/profile_rust.py --verify-only
python scripts/profile_rust.py --output results/rust_profile
python scripts/profile_rust.py --inputs results/rust_profile/inputs.json --output results/rust_packed --confirm-packed
```

维护入口为 `scripts/benchmark_algorithms_rust.py`、`scripts/check_rust.py`、`scripts/profile_rust.py`；诊断源码在 `experiments/rust_profile/`，CI 仅构建及执行短核验，不在共享 runner 上声明性能。
本次原始输入、答案、CSV、内存 JSON、源码快照与独立复核记录保存在本机 `results/rust_performance_20260920/{baseline,packed,packed-final,review}/`。
收口原始记录在 `results/rust_closeout_20260920/`。4 个旧测量脚本及2个过程探针先归档核对再移除；回收约 214 MB 的可重建环境、构建和故意损坏的输入副本，最终 wheel、源快照、原始记录及报告保留。
这些 results 数据尚未发布，不将 Git 代码提交称为本批性能证据的远端冻结。
