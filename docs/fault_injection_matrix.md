# Fault-injection matrix: publication gates

This document records the regression cases in
[`tests/test_fault_injection.py`](../tests/test_fault_injection.py). They mutate
copies of a real `quick` run and check both rejections and known acceptances.

Scope: `configs/quick.json` (run with one worker), artifacts under
`results/_fixture_quick` (gitignored), regenerated by `_benchmark_fixture()`.
The recorded outcomes apply to these mutations and this configuration. Limits
inferred from code, rather than exercised by these cases, are marked separately.
Run the existing cases to repeat the observations:

```console
python -m unittest discover -s tests -p test_fault_injection.py -v
```

## What the checks cover

1. The validator (`.github/scripts/validate_benchmark_output.py`) checks plan
   identities and record consistency, recomputes supported typed statistics
   from `raw_results.csv` and `instances.csv`, and compares the report's checked
   headline section and listed charts. It does not recompute every field or
   artifact; the [output guide](output_schema.md#manifest-and-independent-validation)
   describes the scope.
2. The Manifest (`manifest.json`) records byte counts and digests. The validator
   compares current files with these records. A changed file fails this check
   when the record no longer matches; refreshing the record can restore the
   match. This establishes neither the file's history nor its correctness.
3. The content boundary (`.github/scripts/check_content_boundary.py`) runs in
   `evidence_backed_claims` mode. It permits quantitative prose while continuing
   to reject sensitive content and broken links in tracked files. The retained
   strict mode rejects quantitative claims when selected explicitly. Neither
   mode scans benchmark artifacts under `results/`, and claim-to-evidence
   mapping is reviewed through `experiments/core_rq/CLAIMS.md`.

## Benchmark mutations

For the benchmark mutations below, all cases except the digest mutation refresh
the changed file's Manifest entry before invoking the validator. Acceptance
therefore describes the checks beyond a stale digest.

| Mutation class | Recorded validator result on `quick` | Boundary |
|---|---|---|
| coverage value changed | rejected | The tested coverage-only change leaves an inconsistent gap. It does not establish that every single-file mutation is rejected. |
| selected sets changed | accepted | Greedy and exact-run selections were changed without changing coverage. `quick` has no Lazy Greedy variant, so selection replay is not invoked. |
| gap column changed | rejected | The changed gap disagrees with the recorded coverage and optimum. |
| Manifest digest changed | rejected | The digest no longer matches the file. Changing both together is not a file-history check. |
| seed field changed | raw row rejected; instance row accepted | Raw-run identity is checked against the plan. The instance seed change did not alter a compared relationship. |
| canonical row order reversed | accepted | Reversing either canonical CSV passed. This checker does not enforce the repository's ordering contract for those inputs. |
| feasible status changed to optimal | rejected | A status-only change conflicts with record fields; changing status, coverage, gap, exact flag and bound together conflicts with derived statistics. |
| certificate fields injected | rejected by the record contract | The tested `quick` families reject these certificate fields before proof-value normalization. Certificate-bearing families were not exercised here. |
| unsupported conclusion added to the report | rejected inside the checked section; accepted elsewhere | The first `Headline checks` section is compared through the following `P5.1 descriptive aggregate` heading. Appended text and the tested duplicate section were accepted. |

Code inspection adds two limits not established by these mutations. A fully
consistent re-export of the artifact tree was not tested. The validator also
does not re-verify the set-level proof of a certificate recorded in
`instances.csv`; normalization checks its recorded value against optimal rows
and solver bounds, which is a different check.

The separate [core overlap analysis](../analysis/core_overlap_pilot.py) checks
the pilot's selected sets against regenerated instances and declared coverage.
Those additional checks do not change the general benchmark validator's
acceptance cases recorded here.

## Recorded regression outcomes

The baseline test validates the unmutated fixture before interpreting the
mutated copies. The regression cases record these outcomes:

1. coverage tampered: validator rejected with the recomputed gap disagreement.
2. selected tampered: validator accepted, on both a greedy row and an exact row
   (checksum refreshed). The only selected-vs-coverage replay in the validator
   requires a Lazy Greedy variant, which this configuration does not have.
3. gap tampered: validator rejected with the recomputed gap disagreement.
4. checksum tampered: validator rejected with a digest mismatch.
5. seed tampered: raw-row seed rejected against the execution plan; instance
   record seed accepted. Seed and run_id changed together were rejected at the
   plan-identity step.
6. row order reversed: validator accepted, for both `raw_results.csv` and
   `instances.csv`, with the checksum refreshed.
7. feasible to optimal: the status-only flip was rejected because the record's
   exact flag disagreed with its status; the fully
   consistent flip was rejected at the derived-statistics recomputation.
8. certificate injection: every form tried was rejected by the record
   contract (all-or-none field rule, stochastic-family prohibition, legacy
   constructed-instance prohibition, proof-kind consistency rule). A value
   that conflicts with the solver results never reached the normalization
   stage, because the record contract blocks it first.
9. conclusion without evidence: a fabricated quantitative sentence was
   accepted when appended after the checked section, and again when inserted
   as a second headline section; a value change inside the checked section was
   rejected, and renaming the checked heading was rejected as a missing
   section boundary. The same sentence in a tracked prose file was rejected by
   the strict claim mode and accepted by the active evidence-backed mode; an
   untracked `results/` artifact was not scanned in either mode.
