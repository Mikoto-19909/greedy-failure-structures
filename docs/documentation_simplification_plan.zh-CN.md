## 目标与范围

让读者尽快理解项目研究什么、目前做到哪里、怎样运行，以及在哪里检查结果。
每份文档集中承担一个用途，减少重复说明、抽象宣传和缺少依据的保证。

当前研究检查点是：高重叠实例是否比匹配对照更容易出现非零
optimality gap（算法解与最优解的差距）？这是待验证的问题。
写作时分别说明背景事实、研究推测和实验结果；不能提前把高重叠写成已证实的失效原因。

本轮调整以现有 Markdown 文件为主，同步修正相关模块说明和工作流注释；
只有现有测试依赖被调整的文案时，才同步修改对应断言。
算法、生成器、配置格式、实验语义、输出验证器和 CI 的行为不在本计划的修改范围内。
不为此次精简新增文档框架、写作评分器或风格检查门禁。

本次提交只完善这份计划、调整索引说明并更新许可证清单。
实际文档修正、测试调整和工具脚本清理留待后续实施。

## 实施顺序与验收

实施前确认目标分支、已合并变更和实际工作树；若基线已更新，
只复核受影响的条目，不机械套用本次审查结论。
例如配对分析修复是否已合并、研究结果是否已发布，都需要按执行时的状态判断。

| 顺序 | 工作范围 | 本步验收 |
| --- | --- | --- |
| 先修正事实 | SECURITY、SUPPORT，以及文档、模块说明和工作流注释中的校验和保证 | 运行方式和报告渠道准确；测试不被视为正确性的最终裁判；所有相关说明对校验和能力的描述一致。 |
| 再整理阅读入口 | 中英文 README、分析入口、FAQ、结构机制说明和文档索引 | 读者能找到当前研究问题、进展、最短运行命令与证据入口；研究假设和已有结果明确区分。 |
| 最后压缩共同规则 | CONTRIBUTING、AGENTS，以及前两步涉及的技术说明 | 每项共同规则有明确的主要维护位置；引用有效；强制要求和正确性边界没有被弱化。 |

以上是执行顺序，不要求每个文件单独开 PR。
围绕同一问题修改正文、对应注释和必要测试，放在一起审查；
与本次目标无关的格式整理、源码拆分和工具功能修改另行处理。
配对实验可以继续推进，不能把所有文档整理完成作为启动实验的条件。

## 实验配置与默认入口

在记录的主分支上，README 先展示 quick/full 等工作流，之后介绍较大的 cartography。
CLI 省略命令时运行 quick，PowerShell 包装脚本默认执行 quick，
Dashboard 没有保留的配置选择时也优先选择 `quick.json`。
这些默认行为用于降低启动成本，不等同于当前研究任务的推荐配置。

`quick.json` 和 `full.json` 都是保留的 schema v1 配置，加载时在内存中迁移，
其 dry-run 仍可完成。schema 版本旧本身不是研究设计无效的理由；
关键是实例、算法、参考解和对照关系是否适合本次问题。
这两个配置涵盖多个实例族，没有按当前最小研究检查点组织配对比较。

在中英文 README 的运行说明前加入下面的用途区分，并让 docs/cli 与文档索引
使用相同的描述。用途只在文档中说明，不新增配置字段、分类器或注册表。

| 用途 | 指向哪里 | 如何呈现 |
| --- | --- | --- |
| 当前研究 | 最小高重叠结构效应实验及其配置 | 放在研究入口首位，写明配置是否已经落地、执行前提和运行命令；结果状态由分析入口说明。 |
| 演示与兼容验证 | `demo`、`quick.json`、`full.json` 及明确承担功能验证的配置 | quick 是最短运行检查；full 是较大的既有多实例族工作流，可用于旧配置兼容与回归检查，其名称不代表当前研究的完整方案。 |
| 历史探索与附录 | 阶段性探索配置、较大扫描和附加算法比较 | 保留原位置及完整用法，降低在入门说明中的优先级；注明各自适用的问题。 |

当前研究的具体设计以
[研究检查点计划（PR #23）](https://github.com/Mikoto-19909/greedy-failure-structures/pull/23)
为依据，其中计划新增 `configs/core_overlap_pilot.json`，用普通 benchmark 比较
`high_overlap` 与匹配的 `uniform`，算法为 Greedy 和小实例穷举参考。
核对时 PR #23 只新增计划文档，配置和离线分析脚本尚未成为仓库中的可执行文件。
因此实施文档整理时：

- 配置尚未落地：研究入口链接计划并明确标注待实施，不把计划中的命令包装成可直接运行的快速开始。
- 配置已随研究实现提交：核对所在分支、路径、前置修复和 dry-run 后，再给出显式
  `--config configs/core_overlap_pilot.json` 的研究命令，并链接实际文件。
- 配置内容、样本设计和分析口径由研究计划维护，不在文档精简计划中复制另一份参数表。
  研究实现交付时同步核对入口说明，文档精简不提前创建或改写实验配置。

不能仅按 `p3_` 至 `p7_` 前缀把配置全部归为历史：
`p3_lazy_greedy.json` 仍由 CI 用于功能验证，
`p7_controlled_stressors.json` 用于生成器结构审计，
`pairing_paired.json` / `pairing_unpaired.json` 用于配对方法验证。
这些用途应继续可见，但不能被介绍为本次最小结构效应实验。
`structural_gap_cartography.json` 是更广的结构扫描，
`p6_overlap_scan.json` 是旧的重叠参数扫描，也不能仅凭名称作为当前研究入口。

本轮保留无参数 CLI、PowerShell 和 Dashboard 的实际默认行为，
在相应使用说明中明确它们默认进入示例工作流。
旧配置不批量升级 schema、不移动重命名、不修改参数或 seed；
已有配置哈希、case/run identity 和兼容测试不因用途说明变化而重写。
未来如确需修改默认执行行为，应作为独立行为变更评估。

## 准确性修正的具体边界

SECURITY 的运行方式以 [`dashboard.py`](../src/maxcover/dashboard.py) 中的
实际实现为依据：Dashboard 使用本地 HTTP 服务器，默认绑定回环地址，并拒绝非回环绑定。
这不等于项目没有服务器，也不应被改写成未经验证的远程服务安全承诺。
报告渠道需查看仓库实际设置或可用入口：若私密报告已启用，写明现有入口；
若未启用，只写已核实可用的渠道和限制，不声称已经启用，不虚构联系人，
也不把潜在漏洞细节引导到公开 issue。修改说明本身不包含更改仓库设置。

SUPPORT 将测试描述为行为证据。文档、代码与测试发生冲突时，先核对预期规则、
算法定义和相应实现，再修正错误的一方；测试通过不足以单独决定哪一方正确。
保留命令、配置和错误输出等问题报告要求，无需反复申明维护者不承担服务承诺。

校验和相关表述在以下位置一起核对：中英文 README、output_schema、
fault_injection_matrix、
[`validate_benchmark_output.py`](../.github/scripts/validate_benchmark_output.py)
的模块说明，以及 [tests.yml](../.github/workflows/tests.yml) 的相关注释。
共同表述限定为“文件与记录的哈希一致”；正文可进一步解释记录也可被重新生成。
本步不修改校验算法、拒绝条件或工作流执行步骤。

fault_injection_matrix 的结论应写明配置、变异方式与观测结果。
审查“全部派生产物”等概括时，要与验证器实际检查的字段和报告区段对照。
保留已测得的未检出情况；仅从代码判断、尚未执行的情形继续明确标识。
不得为了使文档看起来完整而把某项盲点改写成已被检出，或顺带扩大验证器职责。

## 表述注意点

每段文字都检查三个问题：能否核对、是否重复、是否已经做到。
优先写具体对象、操作和结果，保留必要的技术术语并在首次出现时作简短解释。

以下为表达方式示例，不是对实现覆盖范围或研究结果的新增声明。
采用示例前仍需核对实际代码与证据。

| 待压缩的表达 | 更具体的写法 |
| --- | --- |
| 构建完整的可复现实验闭环 | 保存配置和种子，并提供重跑命令。 |
| 强化证据链可信性 | 检查分析读取的 CSV 是否与 manifest 中记录的哈希一致。 |
| 系统性揭示贪心失效机制 | 比较高重叠实例与匹配对照的 gap，检查出现差异的实例。 |
| 确保实验结果可靠 | 列明执行了哪些检查，以及这些检查能支持什么判断。 |

尤其注意以下边界：

- 校验和检查说明文件是否与记录的哈希一致。若文件与记录一起改动，
  该检查仍可能通过；它本身不能证明文件从未被改动，也不能证明统计计算正确。
- 独立验证器的说明要列明实际检查范围，不笼统声称它重新验证了全部结果。
  CI 通过也不能替代结论与证据之间的人工核对。
- 演示实例、功能检查和研究实验的用途需要说明，但不必在多个段落反复辩解。
- 双语版本同步维护事实、链接和适用边界。能从配置查到的易变数字尽量不重复写入介绍；
  必须保留的数字应核对同一版本的来源，避免两种语言各自更新。
- 压缩 AGENTS 和 CONTRIBUTING 时，不将强制要求改成可选建议，
  不省略影响正确性或结果复现的条件。约束集中到一处后，应检查引用仍清楚。
- 区分当前主分支、未合并 PR 和已经验证的运行。实施时重新确认状态，
  不把会话中提到的修复自动当作已进入主分支。

## 验证与连带更新

文档调整需要核对命令、相对链接、事实来源和中英文语义。
阅读顺序应能从项目介绍到达研究分析，再到结论对应的证据。

保留目前必要的正确性边界：固定输入与确定性行为的要求、随机算法的显式种子、
超时结果不能充当参考最优值，以及现行的独立验证与证据发布流程。
完整探索输出仍留在未跟踪的 `results/`，公开结论所需的最小证据继续按
CONTRIBUTING 的要求保存。

新增或修改文档会影响 [`LICENSE_MANIFEST.json`](../LICENSE_MANIFEST.json)。
实施时先暂存实际修改，再用现有脚本重新生成清单并暂存清单，运行现行要求的检查。
[`PUBLIC_SNAPSHOT_MANIFEST.json`](../PUBLIC_SNAPSHOT_MANIFEST.json) 和
`docs/history/` 保存迁移历史，不随这轮文案调整重写。

修改正文前检查现有测试是否依赖其中的路径、术语或事实。
不要为了让旧文字断言通过而保留错误表述，也不要为精简文档新增一批只检查措辞的测试。
如果确需同步调整已有测试，应保留其实际验证的行为或事实；
涉及文档规则与执行代码的变更时，遵循 AGENTS 已有的独立审查要求。

按实际变更执行验证，并遵守现行仓库要求：

1. 核对被改写的事实、命令和链接；命令发生变化时执行对应帮助、dry-run 或最短工作流。
2. 如同步修改文档断言，先运行 `python -m unittest discover -s tests -p test_documented_claims.py -v`。
