# R2 可选 CPU/CUDA 生产后端方案

2026-09-08。状态：源码与官方文档调研、小范围独立复核完成；以下为待实施方案，
尚未添加生产后端参数或修改正式执行器。已有成果先保存为本地提交 `ad1224e`。

## 结论与范围

建议先接入逐图 NumBa CPU 后端，再提供单一 GPU 拥有者的显式 CUDA 路径。
首版保留逐图枚举、逐图计时和逐图检查点。跨图批处理、自动 CPU/GPU 分配及流水线
作为后续阶段，先解决批次计时与 F2 估算契约，再实施。

首版只针对 `analysis/r2_budget_grid.py` 的全预算精确枚举，不替换
`src/maxcover/algorithms.py` 的通用 `brute_force`。后者只求一个预算，具有时间限制和
Solution 状态契约，与 R2 的一次全子集扫描不是同一接口。
Greedy、结构指标、交换诊断、统计方法及独立验证保持原计算路径。

## 已有依据与不能直接移植的部分

- [已有归档](../experiments/acceleration_v1/README.md)保存 CUDA 内核、编译 CPU 原型、
  固定输入及测量。全量无绘图流程在仅加速验证后约为 216 秒，生产阶段仍约 110 秒；
  这说明生产值得优化，但不能据内核倍率预告整个流程的 CUDA 收益。
- 生产端已在 `all_budget_optima` 中一次访问所有子集并返回各预算答案，不能将“跨预算
  一次扫描”当作尚未实现的新优化。仍待加速的是 Python 循环及相关执行开销。
- 原型使用 AST/exec 提取旧函数、临时替换函数引用以及按整批结果查表。这些是试验手段，
  不作为正式依赖注入或后端装载方式。
- 原型查表使每图 `enumeration_seconds`、`base_seconds` 排除了真正的批量枚举成本。
  原型外层墙钟计时仍有效；但 `f2_from_preflight` 使用 `base_seconds` 选择网格，
  所以不能直接移植该计时或把批次耗时均摊后称为每图实测。
- 原型捕获全部 `CUDARuntimeError`，会把 `cudaErrorInvalidValue` 等实现问题回退为 CPU
  成功。本次独立复核实际重现了这一行为；正式路径必须缩小错误处理范围。

## 首版接口与行为

以下名称是建议，不是当前已经可运行的参数：

```python
run(design, output, *, workers=4, resume=False, stop_after=None,
    production_backend="python")
```

建议 CLI 为 `--production-backend python|numba|cuda|auto`：

- `python`：默认，保留现有 Python 枚举、默认分发及 patch seam，不导入 NumPy、Numba、CuPy。
- `numba`：严格要求编译 CPU 后端可用，维持现有 1～4 个 CPU 工作进程。
- `cuda`：非空任务必须真正成功执行 CUDA，不静默回退。首版显式要求 `--workers 1`，
  由单一隔离进程持有 GPU；这限制首版 CPU 诊断并行性，因此不承诺它快于 NumBa 四进程。
- `auto`：首版明确表示 CPU 可用性选择：NumBa 可用则用 NumBa，否则警告并使用 Python。
  首版不自动启用 GPU。以后有端到端证据和稳定的 GPU 执行策略，再扩展自动选择。

执行选项不进入研究配置、随机种子、实例身份或数值 CSV。它们与
`--verification-backend` 是两个独立选项；生产器不得调用验证器来取得答案。

首版加速选项仅用于 `run` 和测试 fixture；`preflight`/`freeze` 维持原始 Python 成本基线，
API 和 CLI 都拒绝加速预检。用于原 F2 成本判断的预检生产与验证应固定为 Python。
原 F2 预测只解释其 Python 预检执行策略，不是 CUDA 单工作进程策略的保守上界；
CUDA 首版还会使诊断串行。切换后端仍须执行累计时间、主机内存和输出预算检查，
耗尽时保留检查点停止，不自动改网格或样本。
未来支持加速预检时，需要把实际执行策略纳入成本估算，不能只放宽参数。

## 精确结果契约

保留现有 `all_budget_optima(sets)` 默认接口。内部后端返回同样的三个数值部分：

```text
best[0..M], witnesses[0..M], subset_count
```

- 每个预算都返回恰好 k 个不同原始索引的最优覆盖量，见证为升序且字典序最小。
  重复集合仍是不同候选索引，不预去重或重排输入。
- `k=0` 为覆盖 0、见证 `()`。旧接口的 `M=0` 退化答案 `([0], [()], 1)` 保留，
  可以在分发前直接处理并记为退化计算，不宣称执行了 CUDA。
- 首版加速内核限定 `1<=M<=20`，掩码为真正的非负整数且小于 `2**64`。
  范围/类型检查必须在 NumPy 转换前完成。严格后端拒绝超范围；`auto` 可明确选择
  任意精度 Python。当前 R2 配置本就满足更窄的 `N=M<=20`。
- CUDA 的共享数组长度 21、32 位子集编号和反转位移均依赖 M 上限，不能只改配置扩大规模。
  在上述范围，`score=(coverage<<M)|reversed_subset` 最大为 68,157,439，小于 `2**27`。
  覆盖量严格优先；固定 k 时，反向位编码较大对应字典序更小的升序索引组。
- `subset_count=2**M` 是外部结果约定。GPU 原型的该值是推算值，不是实测计数；应在测试
  内核中独立检查线程覆盖数量，并测试错误的启动范围。只有内核完成、同步和结果检查
  全部成功后，才能返回完整结果。不能把声明的计数当作独立正确性证明。
- 主机核对返回数组长度、每个见证的长度/范围/唯一性/排序，以及见证覆盖量与值相符。
  原有独立验证器继续重算全部要求，不能以这些生产端快速检查替代独立验证。

## 分发、GPU 拥有者与恢复

建议流向保持为：

```text
配置/检查点验证 → 按 ID 过滤已完成任务 → stop_after 截取
  → 选择工作进程策略 → 每图生成 → 延迟初始化并求全预算答案
  → 主机检查 → 原有 Greedy/诊断/结构计算 → 原子保存完整图
```

CPU 路径可用顶层函数和可序列化的执行选项传给现有 spawn 池。
建议给 `evaluate_task` 增加仅关键字的后端选项；默认路径仍直接调用现有
`all_budget_optima`，非默认路径调用一个新的独立生产后端模块。
不需要同时重构通用 benchmark facade。

CUDA 使用单一拥有者，避免在四个 CPU 工作进程中各建一个 CUDA context。
建议隔离为一个 spawn 工作进程：父进程继续负责检查点保存，只传普通主机输入和结果，
不传 CuPy 数组、RawKernel 或 CUDA context。拥有者存活期间复用编译内核和小型缓冲区。
首版不把 CPU 诊断拆成另一套池；该拆分属于后续吞吐优化。

已完成恢复运行应在初始化可选后端之前完成“零待办”返回。未完成恢复允许换执行后端，
但输入配置必须相同、旧图字节不变、只处理未完成图；运行记录明确标出后端混用，
不能将混合恢复的时间作为单一后端基准。新尝试不得沿用旧成功状态冒充本次完成。

严格 CUDA 失败时终止本次运行并保留完整图检查点；未写出的图恢复时可重算。
不保存部分 GPU 输出，不把异常转换成 `optimal`，也不自动减少输入规模或删掉难图。

## 计时、错误与资源

逐图首版让后端求解发生在原来的枚举计时区间内：首次初始化、输入打包、H2D、内核、
同步、D2H、输出解码及允许的失败尝试都计入对应墙钟。外层运行时间另包含工作进程启动、
排队和 I/O。使用阻塞回传或显式同步后再停表；CuPy `asnumpy` 默认阻塞。[1]

请求后端、实际后端、首次初始化、设备信息和回退原因写入执行层记录，建议新增仅用于
非默认运行的 `production_backend.jsonl`；不能塞入 seed/hash 或重定义数值 CSV。
首版不引入批次均摊时间字段，保持原图计时含义。未来批处理须使用独立批次时间记录，
并重新设计受其影响的图时间和 F2 估算；不能用查表耗时占位。

错误策略按阶段与明确类型/状态码定义。CPU `auto` 仅对可选依赖或受支持的初始化失败
回退；非法输入、错误答案、断言和程序逻辑错误继续失败。CUDA 首版严格失败；未来
自动 GPU 回退只考虑已列明的环境/资源错误，必须丢弃该次设备输出并保留失败成本。
`cudaErrorInvalidValue`、非法地址和错误启动不得作为普通可用性失败处理。
官方说明非法地址/某些启动超时会使进程状态不一致，需要结束并重建进程。[2]

现有进程 RSS 检查不代表显存使用。GPU 须另限内存池、观测实际空闲显存并留出 context
余量。CuPy 会缓存已释放块，且 context/库句柄占用不计入池上限。[3]
本次本机只读查询是 RTX 4060 Laptop、约 8 GiB 总显存、约 1 GiB 空闲；可用量会变化，
不能按整块显存设计预算。具体池上限及缓冲区尺寸在小预检前固定。

## 依赖和 Windows

生产模块默认导入不得触发可选依赖或环境修改。CPU 候选使用现有测试版本
Numba 0.67.0 / NumPy 2.3.5；新增明确的生产 CPU extra，避免把用途藏在验证 extra 中。
CUDA 候选为 CuPy 14.2.0 + CUDA 12.x，并在独立环境验证 wheel 组件组合。
官方支持 `cupy-cuda12x[ctk]` 在已有驱动下安装 CUDA 组件，无需预先系统级安装 Toolkit。[4]
已有最小环境只安装 runtime/NVRTC 的经验不能替代正式安装路径验收。

NVRTC 曾无法读取包含中文用户名的临时源码路径。正式实现应在隔离的 GPU 进程内处理
ASCII 临时/缓存目录，必要时允许显式指定路径；找不到可用目录时给出可操作错误。
不在模块导入时修改整个主进程的 TEMP、CUDA_PATH 或 tempfile 全局状态，不依赖旧试验目录。

## 分阶段实施与验收

1. **CPU 生产后端。** 整理原型 NumBa 函数为正常模块，接入逐图接口和 `python/numba/auto`。
   保留默认分发及结果；实际测试缺少依赖、初始化失败、非法输入、fresh/resume/stop_after、
   spawn、已完成恢复不导入依赖、旧图字节不变及三个 CSV 一致。
2. **受限 CUDA 生产后端。** 实现单一 GPU 拥有者、显式 CUDA、输入/启动/输出边界和显存限制。
   实际执行重复/全空集合、最高位、全 64 位掩码、M=20、k=0、返回缺项、同步失败及错误码测试。
   与 Python 原实现、独立集合枚举及现有验证器交叉核对。
3. **先验收，再扩吞吐。** 先固定小样本比较 kernel 与含启动的单图成本；通过后比较实际
   Python 四进程、NumBa 四进程和 CUDA 首版的完整流程，明确各自执行资源。验证后端统一。
   不把 CUDA 单工作进程与 CPU 四进程的差异称为纯硬件倍率，不承诺 CUDA 必胜。
   全量验收复用现有 1,800 图、13,000 预算，每方式三次新输出，包含全部诊断、验证与 CSV。
4. **有收益依据后再做跨图批处理。** 在检查点过滤后按相同 M 组成有界批次，保留任务索引
   映射并检查返回图数；不得按掩码字典或截断 zip 隐藏映射异常。设计批次计时、F2 适用范围、
   失败批次的同输入处理和已保存图恢复，再评估 GPU 计算与 CPU 诊断流水线。

生产/辅助模块按现有研究检查规则登记。CPU 必需检查真实运行 NumBa，并检查 Python 回退。
GPU 检查提供显式命令：缺少 GPU/依赖就失败，不能以 skip 声称 GPU 验证通过。
普通 CPU CI 可覆盖边界和回退，但不能替代实际 GPU 验收；默认 Ubuntu CI 没有已确认的
CUDA 硬件，应先保留本机真实 GPU 运行与独立复核证据，后续再决定 GPU CI 的运行位置。
