# 删除门禁后，实验与新研究任务交付快了多少？

在本机的固定对比中，quick 新运行、完整 checkpoint 的 resume 和 R1 离线分析
都呈现较低的中位耗时。加入同一组 R1 文件并完成全部本地检查、提交的流程，
本次从 269.23 秒降到 166.50 秒，减少 102.73 秒，约 38.16%。这支持减少当前
研究流程执行负担的判断；它没有测量模型推理速度，也不能代表任意新任务的总交付时间。

## 比较方法

按[测量设计](gate_speed_comparison_design.md)，对照 PR #46 前的
`891c389287bd4fa6adf21a712b8ddab5aa2a4a39` 与合并后的
`285c3b09d8e585eb36f7df9dc986728ab4f12550`。在同一 Windows 11 主机、Python
3.12.14、mypy 2.3.0 和 Matplotlib 3.11.1 环境中使用独立本地副本。
算法、模型、配置模块和实例生成器没有版本差异；两边加入完全相同的五个任务文件：
R1 分析程序、独立验证器、JSON/Markdown 设计及功能测试。

实验命令每种先预热两版，再串行执行 7 对测量，交替两版的先后顺序。quick 使用
`configs/quick.json`、单 worker，共 48 条算法运行记录；新运行每次使用新目录。
resume 重复运行同一 benchmark 命令，由默认续跑行为读取已完成的 checkpoint，
跳过已完成的算法任务。R1 每次重新分析 60 个 pilot 实例和 6 个功能样例，不绘图。
计时包含进程启动、输入检查、文件读取及输出写入，不能解释为求解器内核加速。

完整交付流程每版各运行一次，顺序为旧版、新版，从新的干净副本开始。先暂存任务，
执行 R1 和独立重算，再运行该版本 CONTRIBUTING 对应的全部本地检查，最后实际
本地提交。旧版还包含许可清单生成/暂存、内容、许可和提交检查。源码副本准备、
依赖安装、编写任务文件、模型推理、人工审查及网络/CI 等待不在这项计时内。

## 实验命令结果

| 工作负载 | 成功配对数 | 旧版中位数（秒） | 新版中位数（秒） | 配对耗时比中位数（新/旧） | 对应耗时减少 |
| --- | ---: | ---: | ---: | ---: | ---: |
| quick 新运行 | 7 | 1.5315 | 1.0460 | 0.6826 | 31.74% |
| 完整 checkpoint 的 resume | 7 | 1.2304 | 0.7707 | 0.6203 | 37.97% |
| R1 离线分析，不绘图 | 7 | 0.7564 | 0.7005 | 0.9410 | 5.90% |

比例列先对每一对求 `新耗时/旧耗时`，再取中位数；它不是两列版本中位数的商。
quick 和 resume 的 7 对均更快。R1 的 5 对更快、2 对略慢，差异较小，不能保证
单次运行必然改善。R1 计算代码相同，既有 pilot 输入检查器随版本变化。

全部成功配对的稳定 quick 原始记录（排除 `runtime_seconds`）与实例数据一致；
R1 的完整轨迹和两张 CSV 逐字节一致。新版较短耗时并非通过少算 R1 实例得到。
详见[逐对数据](../experiments/gate_speed_comparison_v1/paired_times.csv)和
[汇总](../experiments/gate_speed_comparison_v1/summary.csv)。

## 新任务的可重复本地交付流程

| 本次有效流程 | 旧版 | 新版 |
| --- | ---: | ---: |
| 已完成步骤 | 12 | 7 |
| 所有步骤耗时之和（秒） | 269.2267 | 166.4986 |
| 流程墙钟耗时（秒） | 269.3150 | 166.5699 |
| 完整 unittest 命令耗时（秒） | 259.2302 | 160.3382 |
| 发现的测试数 | 610 | 403 |
| 通过 / 跳过 | 608 / 2 | 402 / 1 |
| mypy 检查源码文件数 | 39 | 38 |
| R1 独立重算 | 66 个实例通过 | 66 个实例通过 |
| 全部适用检查及本地提交 | 完成 | 完成 |

总差值 102.73 秒中，约 98.89 秒来自本次完整 unittest 命令的差异。两版检查集
不同，因此这些数字主要说明简化后维护和执行整套检查所需的成本降低，不能把全部
改善归结为单个 SHA256 操作。两版缺少可选 OR-Tools，跳过项已在日志中注明。

完整流程也产出相同的 R1 数据，且两版都成功提交；失败的流程没有计作完成。
提交发生在测量用隔离副本，未推送。见[逐步命令及状态](../experiments/gate_speed_comparison_v1/workflow_steps.csv)
和[有效流程汇总](../experiments/gate_speed_comparison_v1/workflow_summary.csv)。

## 异常与解释范围

旧版出现两次正式 fresh 运行的 `WinError 5`（原子替换 CSV 时文件访问失败），
以及一次 checkpoint 准备失败。原始记录保留这些失败；受中断的整对重新测量后，
只将完整成功的配对计入统计。上表是以成功为条件的耗时，不能据此证明文件访问
问题由门禁引起，也未估计包含重试在内的长期平均交付时间。

最初一次旧版完整流程因测量脚本设置 Git 作者/提交者环境变量，干扰了测试中刻意
设置的身份而作废，已标记 `invalid_harness_workflow`。修正为私有 Git 默认配置后，
在两个新的干净副本中重新执行了表中的有效流程。被中断的测试没有完整计时行；
其日志仍保留。详见[异常说明](../experiments/gate_speed_comparison_v1/measurement_notes.txt)
及[全部原始命令记录](../experiments/gate_speed_comparison_v1/raw_times.csv)。

本次只有单机、每命令 7 对和每版一次完整流程。系统缓存、文件系统或杀毒活动，
以及完整流程先旧后新的顺序都可能影响差值；不据此作显著性或普遍比例保证。
本次实际研究任务还包含设计、工具编写、独立审查、报告整理、性能测量以及 Git
工作树登记修复。任务计时器延续原目标并允许中途修改，不能将累计时长直接当作
这批研究的独立端到端耗时；之前任务也没有相同范围、相同计时口径的基线。
因此能回答“固定执行与交付步骤是否变快”，尚不能量化整个新任务比之前快多少。

计时设计中原拟记录的独立端到端时长未能取得。作为可核对的执行上下文，
2026-09-06 20:12（UTC+8）读取目标计时器为累计 5,191 秒（86 分 31 秒）；
这是跨目标修改的累计快照，不是单独 R1 任务或最终完成时长，不参与速度比例计算。

## 复现与数据

安装项目及分析依赖，并确保本地 Git 含上述两个提交及有效的提交身份后执行：

```console
python -m pip install -e ".[typecheck]" matplotlib
python analysis/compare_research_workflow_speed.py --source . --output results/gate_speed_reproduction --pairs 7
```

如果遇到命令失败，先查看输出目录日志；仅在解决外部原因且尚未进入完整流程时，
可用同样参数加 `--resume` 保留完整配对并重试中断部分。已开始的完整流程用新的
输出目录和 `--workflow-only` 重测。脚本在副本中执行必要的旧版检查和本地提交，
没有把已移除的检查重新接入当前开发或 CI。

保存的数据位于 [experiments/gate_speed_comparison_v1/](../experiments/gate_speed_comparison_v1/)，
包含原始时间、配对汇总、有效流程步骤、运行环境和异常说明。CSV 中的 `log` 是相对
该测量目录的日志位置，`output_directory` 是相对各隔离源码副本的临时输出位置；
副本及其整套实验目录保留在本地 `results/`，不随这份报告归档。
